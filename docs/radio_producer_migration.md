# Radio scheduler producer migration (#42–#44)

All application-managed radio operations that use `app.services.radio_runtime.radio_runtime.radio_operation()` now enter the **one process-owned** `RadioJobWorker`. The only lower-level transport entry point is `radio_runtime.raw_radio_operation()`, which the worker uses to acquire `RadioManager._operation_lock`. Initial connection, post-connect setup, disconnect and reconnect keep their lifecycle-only manager lock, rather than creating a second MeshCore owner. A regular running server fails closed if the worker is unavailable; isolated pytest unit tests may use the old context with fake transports.

## Scheduling and delivery semantics

* User message operations are high priority, settings/manual advertisements/repeater and room queries normal, periodic polling/sync/adverts/telemetry low. The scheduler's bounded queue, aging and capacity rules remain authoritative. `blocking=False` maintenance work **skips** when any queued/executing command exists; it never creates a growing backlog or an extra unsolicited advertisement.
* Legacy HTTP operations retain existing synchronous JSON and status codes. An admitted *job* is an observation of the command stage, not a delivery guarantee; message delivery and channel echo status still come solely from the existing SQLite/ACK/echo code paths. A transport timeout remains ambiguous. The scheduler never silently replays uncertain transmissions after reconnect or restart.
* Direct-message first-send jobs attach the existing durable message ID and firmware ACK code while still in the worker command stage. Further ACK codes from deliberate firmware-guided retries are associated with the **same** logical waiter. Only `dm_ack_tracker` → SQLite may confirm them; packet observations are not independent proof. DM retry and channel echo watchdog radio commands are now worker-admitted (not extra lock owners). The original retry count, firmware timeout, final flood attempt, sender timestamps, SQLite dedup, channel slot cache and `finally`-based flood/path-hash restoration are retained.
* Repeater and room login endpoints reserve a target-scoped reply listener **before** worker submission and release the worker command permit after `send_login`. They can therefore coexist with independent DM ACK waits. Same-target new attempts remain conservatively fenced within a radio generation because the firmware supplies no request ID. The at-most-one direct-to-flood fallback is performed in the **same** logical reply session after an unconfirmed attempt; explicit rejection never triggers flood retry. Existing API response shapes remain unchanged.
* CLI and other firmware query endpoints lack sufficient request correlation to safely interleave arbitrary commands. They are serialized by keeping the worker command section for the **entire** legacy reply/polling scope, including `_flush_pending_messages`. They cannot falsely attribute an unrelated response to a new scheduler job. Inbound RF packet callbacks themselves are not enqueued behind outgoing work.
* Radio settings PATCH validates firmware capability before changing anything and attempts restoration of known effective settings when a later operation fails. This is **compensating rollback**, not an atomic firmware transaction; a failed compensation is exposed as HTTP 503 and requires operator intervention. Path/flood-scope overrides stay inside an uninterrupted command section.
* Reboot and private-key import invalidate radio-generation assumptions and channel/contact slot caches; connection/reconnection already advances the manager generation. The single worker fences stale job results. Never run `uvicorn` with multiple workers on the same device.

## Deliberate V1 limitations / operator verification

Legacy send and CLI endpoint compatibility has priority over switching all writes to HTTP 202. The API includes read-only job snapshots and cancellation, but this migration **does not** enable arbitrary command submission or claim physical TX/RX status. Existing synchronous CLI polling can still occupy the command permit throughout its bounded wait; future protocol-specific correlation is required to relax that safely. Jobs are in-memory and vanish on restart, while outgoing message records remain durable in SQLite. Manual hardware tests should cover serial/BLE/TCP reconnect, startup/setup, repeater/room login and route fallback, DM ACK retries, channel echo watchdog, periodic sync cadence, scoped channel sends, and config rollback behavior when the device rejects a mid-update step. If a command times out beyond the worker's deadline, the worker is quarantined: restart the process after checking radio state; never automatically resend ambiguous packets.

## Static migration audit

The worker's internal `raw_radio_operation` use and `RadioManager`'s lifecycle/setup/transport-lock functions are the **only allowed direct radio-lock owners**. All ordinary router, background, message-send and fanout producers must import the `radio_runtime` seam rather than the manager directly. Add a regression test whenever a new producer enters the transport layer.
